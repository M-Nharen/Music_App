# Qwertone plan

This file is the shared memory between build sessions. Each session: read it, build the next part, update the status and notes.

## About the user

- Arch Linux, Hyprland with the end4 (illogical-impulse) rice. Wayland.
- Total beginner at music, so explain things plainly in the app.
- Galaxy Buds Live (SBC/AAC on Linux) and Sony WH-1000XM4 (SBC/AAC/LDAC). Wired earphones planned later. Bluetooth must stay a first-class case.
- Spotify Premium, and the only user (a personal Spotify developer app is fine).
- Wants every key/keybind customisable and the app easy to play.

## Decisions

- **Rust** for the app and audio engine (no GC pauses). **egui/eframe 0.37** for the UI.
- **cpal 0.18 with the native PipeWire backend** (feature `pipewire`, on by default), with ALSA as the fallback. Buffer is a fixed 128 frames by default (2.7 ms at 48 kHz); `node.latency` gets set from it.
- Sound: **rustysynth** SoundFont player (FluidR3 from `soundfont-fluid`), plus a small built-in additive synth as the fallback.
- Input: egui key events, read in `raw_input_hook` before widgets see them. Uses physical keys, ignores key repeat, and releases all notes when the window loses focus. (Option for later: an evdev thread for even lower input latency.)
- Config: plain TOML in `~/.config/qwertone/`, reloaded when the file changes.
- Python is only used for the offline song analysis in Part 6 (Demucs, Basic Pitch, CREPE, chord detection), as a separate tool that writes song files.
- Spotify can't provide audio for splitting into parts (against its terms). Spotify is used for search, remote control, now-playing and sync. Splitting and note extraction run on the user's own audio files or on MIDI.

### Lyrics notes (Part 10)

- Spotify's lyrics can't be used (no public API; licensed to Spotify). Lyrics come from local files, LRCLIB, or are generated. Spotify (Part 8) only supplies title/artist/duration/position for lookup and sync.
- The user mostly listens to Tamil songs. Show three toggles per line: Tamil script, Tanglish (romanised), English (machine translation, labelled as such).
- egui 0.37 shapes text with harfrust, so Tamil renders correctly when a Tamil font is loaded (`noto-fonts` has Noto Sans Tamil); add it as a fallback font.
- Source info is kept separately for words / timing / translation, per song and per line where it differs (e.g. user edits), with the URL or file and fetch date, so the app can show a "where these lyrics came from" badge.
- Lyric timing uses seconds and beats (like notes) and the same Bluetooth latency offset as Song mode.

## Notes for the next session

### From Part 4b (looper, virtual MIDI out, more instruments)

- **Branch:** `part-4b-loop` = `part-4a-record` + 4b. Doesn't touch `analyzer/` (10a-lite was being built alongside on `part-10a-lyrics`). Part 7 starts here after merging `part-10a-lyrics`.
- **Looper runs in the audio thread** (`audio/looper.rs`, `Command::Loop(LoopCommand::…)`): `Rec { count_in, bars }` (one key does start → close → overdub → keep, decided from the state in the audio thread), `TogglePlay`, `Stop` (Escape/panic only; `AllOff` from losing focus keeps the loop going and just closes held notes of a layer being recorded), `Undo` (cancels the layer being recorded, else drops the newest; dropping the last one clears), `Clear`, `Mute(i)`. States: Empty → CountIn → First → Playing ⇄ Stopped.
- **No allocation in the audio thread:** 8 layer slots × 4096 events are allocated in `Looper::new` (on the UI thread, with the `Renderer`); removing a layer only `clear()`s it; insertion is a sorted `Vec::insert` within capacity; closing the first layer uses `sort_unstable_by` (in place). A layer that fills up stops taking note-ons (`full`, shown on its chip) but keeps room for offs.
- **Timing model:** event positions are in **beats** (f64) from the loop start, with a `pass` tag: an event recorded in pass k plays from pass k+1 on (so overdubs loop back without doubling what you just played, and notes held across the wrap close in the next pass). The loop clock is `anchor_beats + (sample − anchor_sample) / beat_samples`; a tempo change re-anchors, so the loop stretches instead of drifting. `Looper::next_time()` joins the sequencer's split points in `render_block`, so loop playback is sample-accurate. First layer: fixed `bars`, or free (`bars = 0`: the second press sets the target to the nearest bar line, at least 1 bar; notes played just past it fold into the start of the loop in pass 1; auto-closes at 64 bars). An empty first layer leaves no loop.
- **Metronome lock:** a new loop starts on a click after `count_in` beats (if the click was off, the looper switches it on for the count-in + first layer only: `Renderer.loop_click`). Every pass start (and play / restart) re-aligns the clicks with accent on the loop's beat 1 (`align_clicks`); `Click(true)` and `Tempo` snap to the loop's next beat (`Looper::next_beat`). A 4a take started while a loop plays begins at the top of the next pass (`next_pass_start`), no count-in.
- **Channels:** each layer plays on channels lent from a pool (15, 14, …, 10, 8, … 3; 9 = drums stays 9), one per source channel (0 melody / 1 chords / 2 bass) it used, with the program that channel had when the layer's first note there was recorded (`take_program` → `Renderer.loop_programs`, also tapped into a running take as a program change). So layers keep their own instrument and a loop note never cuts a key you hold. Out of channels → shares yours. **Song mode uses 3–8, 10–15 too:** a song loaded while a loop with many layers plays can steal a layer's instrument. Part 7 should keep them apart (e.g. stop the looper in Song/Jam mode, or reserve 13–15).
- **The tap:** `tap(rec, looper, programs, t, e)` = what the 4a recorder sees also goes to `Looper::record` (your notes, sustain-delayed offs, sequencer chords/arps/patterns + pattern drums, drum keys). Loop playback goes to the recorder (so a take includes the loop) but not back into the looper. `ChannelNote` / song playback aren't looped.
- **UI** (`ui/app/looper.rs`): `LoopStatus` is copied into `Stats.looper` every buffer (`try_lock`); the looper bar on the Play tab under the recorder (buttons, length picker locked while a loop exists, a timeline with beats/bars and the playhead, a chip per layer: click = mute). Clear needs two presses within 2 s (`LoopUi.clear_armed`). A loop doesn't survive an audio restart (buffer size change / Restart audio).
- **Keys** (remappable; actions `loop`, `loop-play`, `loop-undo`, `loop-clear`, `loop-mute <1-8>`, the first four + mute 1–4 in `CONTROLS`): F10 loop, F11 play/stop, F12 undo, Delete clear. Added to saved layouts without them (`ensure_loop_keys`, marker text `loop-play`) where the key is free. Delete is also the note editor's delete key; the editor sees keys first, so no clash there.
- **MIDI out** (`midiout.rs`): an ALSA sequencer client "Qwertone" with one port "out" (`create_simple_port`, READ|SUBS_READ). PipeWire exposes ALSA seq ports through its MIDI bridge, so no separate PipeWire MIDI code (a native `pw_filter` MIDI port could replace it later). The audio thread `try_send`s `MidiMsg { at, data }` (stamped with the buffer position's time) into a bounded(4096) channel; the `qwertone-midi` thread sleeps until `at` and sends with `event_output_direct`. All sound goes through `Out` / `out_event` (synth if `local`, + MIDI); song playback through `song_event` (MIDI only with `midi_out_song`; always heard here unless it goes out). Program changes go out when set and for all channels when MIDI out turns on; `AllOff` sends CC 123 on all channels; closing the port does too. Config: `midi_out`, `midi_out_song`, `midi_out_local` (Audio tab card; header shows a "MIDI out" chip). `apply_midi_out()` runs after every engine start.
- **Instruments:** 16 appended to `INSTRUMENTS` (old indices unchanged, tested): harpsichord, celesta, xylophone, kalimba, steel drums, clean electric guitar, sitar, violin, cello, pizzicato strings, trumpet, brass section, alto sax, clarinet, pan flute, shehnai. Built-in synth patches for the new families (bowed strings, plucked strings incl. harp, which used to get the slow pad, brass, clarinet, reeds/shehnai, sitar-type plucks, kalimba/steel drums); `Visual::for_program`: sitar & co. → fretboard, brass/reeds → waveform.
- **Tests:** looper unit tests (fixed/free length, nearest bar both ways, count-in, overdub across the wrap, mute/undo/clear + channel lending, stop/play, tempo stretch, full layer never grows), a renderer test (count-in clicks, loop on channel 15 with its program, MIDI out bytes, MIDI-only mode silent), MIDI thread ordering/timing with a fake sink, every instrument sounds and stops.
- **Not checked on real hardware:** the ALSA port (no sequencer in the build sandbox; the "can't open" message was checked), how the looper feels at real speed (the headless ALSA null device runs faster than real time; the states and UI were clicked through headless, the timing is covered by tests).
- **Ideas not done:** quantise a layer, per-layer volume, saving / loading loops (and exporting the loop as MIDI: the 4a recorder can already capture it), a "double the loop length" button, syncing the accompaniment rhythm to the loop's bar, MIDI in (play Qwertone from a MIDI keyboard), MIDI clock out.

### From Part 4a (metronome, recording, MIDI export)

- **Branch:** `part-4a-record` = `part-5-songs` + 4a. Build 4b (looper, virtual MIDI out) from it.
- **Recording runs in the audio thread:** `Renderer.rec` taps every event *you* cause (your notes on ch 0 incl. sustain-delayed offs, the sequencer's chords/strums/arps/patterns on 1–2 + pattern drums, drum keys on 9, program changes on 0–2, `AllOff`) and `try_send`s `(samples since start, RecEvent)` to a bounded channel (`Engine.recorded`). Song playback and `ChannelNote` (one-key / editor audition) aren't recorded. The UI drains it each frame into a `record::Take`.
- **Count-in** is sample-exact: `Command::Record { on, count_in }` restarts the clicks (~50 ms lead) and sets the start to `next_click + count_in × beat`; anything earlier is dropped. If the metronome was off it clicks only for the count-in (`Metronome.off_at`). `cfg.count_in_beats` (default 4, 0 = none).
- **Metronome:** the old latency-test click got `Command::Click(bool)`; a user click follows `Command::Tempo` (one shared tempo with the rhythm, `cfg.tempo`), accent every 4 beats. Not synced to the rhythm's bar yet. Not saved between runs.
- **Export:** `Take::to_midi` = type-0 SMF, 480 TPB, the current tempo, 4/4; open notes closed at the end (drum hits get a short off). Saved as the next free `~/Music/qwertone/take-NNN.mid` (XDG music dir). The app's own MIDI reader opens them (tested).
- **Keys** (remappable, new actions `metronome`, `tap-tempo`, `record`): F5 metronome, F6 tap tempo, F7/F8 tempo −/+, F9 record/stop. Added to saved layouts that don't have them yet (`ensure_record_keys`), where the key is free. UI: a bar on the Play tab under the chord/drum panel.
- **Not checked on real hardware** (built and unit-tested only). Ideas: punch-in, quantise on export, record the song backing too, tempo changes mid-take (export uses the tempo at stop).

### From Part 5 (Song mode, note editor, live listen)

- **Branching:** `part-5-songs` = `part-3-learn` + `part-6-analyzer` merged (clean, it only adds `analyzer/`) + Part 5. Part 4 hasn't been built yet; it should branch from `part-5-songs`.
- **Layout:** pure logic in `src/song/` (tested, no egui): `mod.rs` (the `song.json` model, `BeatGrid` for seconds ↔ beat positions and bar numbers, `songs_dir()`), `midi.rs` (any `.mid` → `Song` with `midly`; tempo map, meter, key signature, analyzer `chord:`/marker texts, guessed chords; and writing `song.mid` / `midi/<part>.mid` with a beat-following tempo map), `chords.rs` (chord templates + Krumhansl key finding, roman numerals; shared with live listen), `practice.rs` (targets, timing windows, wait / one-key / loops / scoring, the heard-clock formula), `layout.rs` (auto song layout), `library.rs`, `analyze.rs` (spawning the analyzer), `edit.rs` (editor model + saving). Audio: `audio/songplay.rs`. Live listen: `src/listen/` (`mod.rs` DSP, `input.rs` cpal input + thread). UI: `ui/app/song.rs`, `ui/app/listen.rs`, `ui/song_view.rs` (falling notes, chord sheet, timeline, piano roll).
- **Song model:** `Song::load(path)` takes a song folder, a `song.json` or a MIDI file. Unknown JSON keys are ignored; other formats and newer `format_version`s are rejected. `Song::chords_for(part)` / `key_for(part)` give the transposed `simplified.chords` / key for transposed easy parts. Test fixtures in `tests/fixtures/` come from the analyzer's own 27-second test clip (`clip-midi.song.json` from its MIDI, `clip-audio.song.json` from the mix without stems: all its melody notes are low-confidence, handy for the editor), plus `clip.mid` and the clip's `clip-truth.json` (the real chords).
- **Playback runs in the audio thread** (`SongPlayer`, `Command::Song(SongCommand::…)`): sorted note events (`SongData`, built by the UI, kept alive in `SongUi.retired` like patterns), its own song clock with speed, loop (`Loop(a,b)` jumps back sample-accurately and bumps `loops`), `Wait(Some(t))` (stops exactly at `t`; notes *at* `t` wait too), mute bitmask per track (track = part index, 63 = metronome clicks). `Renderer::render_block` splits buffers at song events like it does for the sequencer. The position is published in `Stats.song_clock` (`try_lock`, never blocks audio). Parts play on channels 3–8, 10–15 (`ChannelProgram` for any channel now; `Renderer.programs` has 16 slots; channel 9 skipped); drums on 9; you stay on 0–2. `Command::ChannelNote` plays a note on any channel (one-key mode, editor audition). `AllOff` (Escape, window losing focus) also pauses the song.
- **Bluetooth sync:** `heard_delay_ms()` = the device's measured latency (else typical Bluetooth delay, else reported + buffer) + the *Nudge* (`cfg.song.offset_ms`). `practice::heard_time` turns the audio clock into what you hear now: `pos + (since − delay) × speed`; when the song has stopped (wait / pause) the sound before the stop is still on its way, so it keeps moving until it reaches the stop. The UI keeps it monotonic between seeks/loops (after a resume the first sound is still in flight). Everything (falling notes, chord sheet, hints, scoring) uses this heard time. Timing windows (`Settings::with_latency`): perfect 60 ms + 10 % of the delay, good 150 ms + 25 %, and late presses get Part 2's grace on top (`grace_ms() − 80`). Windows are real time, so at 50 % speed they're half as long in song time.
- **Practice rules:** targets = notes of the parts you play (moved by whole octaves to fit your keys, `best_octave_shift`) + the chord sheet as chord targets. Targets with no key in the layout are drawn as outlines and never asked (`playable`). "Any octave counts" (default on). Chords count when the root + triad match (G for G7), from a chord key or from held notes. Groups = targets starting within 45 ms; wait mode waits for a whole group. One-key mode plays the group's real notes (chords voiced around the chord centre) and scores the timing. A loop pass is scored on its own (`Practice.pass`), shown as bars; auto speed-up +5 % after ≥ 90 %. Best accuracy per song id (`fingerprint` / path) in `cfg.song.best` (only at 100 % speed, not one-key).
- **Song layout** (`layout::build`): writes `keymaps/song.toml` and switches to it (the previous layout is remembered and restored when it's unticked). Chords are a new `ChordRef::Named { root (absolute pc), kind: ChordKind }` (keymap text `chord G7`, `chord F#m`; names start with A–G, roman numerals never do), so they play the same chord whatever key the app is in; modifiers still work. More than 21 chords → 7ths become triads, then the rarest share the closest chord's key. Notes are `note n` relative to the base note when built.
- **In Song mode chord keys play block chords** (`send_style` checks `song_ui.style_overridden`): a pattern or arpeggio would fight the song.
- **Easy parts with `transpose != 0`:** the backing (other parts) is moved by the same amount so it matches, and the UI says it won't match the recording. When Part 7 plays the stems instead, they need pitch-shifting (or play the original part).
- **Analyzer from the app:** `analyze::find_analyzer()` (PATH, then `~/.local/bin`), `Job::start` spawns `qwertone-analyze FILE --json-progress --mode … [--simplify -d N] [--no-separate]`, a thread reads stderr line by line (`parse_line`), stdout is drained. Progress = weighted stages expected for the mode (`expected_stages`, stems weigh the most), creeping inside a stage; `done` gives the folder, which is opened. Errors show the last log lines. Tested with a fake script and with the real analyzer (light install).
- **Note editor:** `Editor` edits in beats (snap 1/4 by default), keeps seconds in step through `BeatGrid`, undo/redo, Tab = next unsure note. Saving (`edit::save_part`) rewrites only that part's `notes`, `note_count`, `low_confidence_count`, `pitch_range` in the JSON (everything else, known or not, is kept), adds the part id to `analyzer.options.edited_parts`, keeps a one-time `song.json.bak`, writes atomically, then rewrites `song.mid` and `midi/<part>.mid`. Every note touched (or confirmed with Enter) gets confidence 1.0. MIDI-file songs save `<name>-edited.mid`. Chords can't be edited yet.
- **Live listen:** `listen::Analyzer` = 8192-point FFT every 2048 samples. Chroma from spectral peaks with overtone suppression (a peak at 2–6× a much louder lower peak counts 25 %) and magnitude^0.75; chord = templates (`song::chords::best_chord`, 7ths only when the 7th is really there), sticky (a new chord must win twice). Notes = harmonic sums with checks that the fundamental is a real peak and isn't an overtone. Melody pitch = YIN (70–1200 Hz). Key = Krumhansl on a ~20 s decaying chroma. On the analyzer's test mix it names 96 % of the frames right. Input picker lists cpal inputs; PipeWire "monitor" sources let it follow Spotify. Results go through `Arc<Mutex<…>>`; the thread repaints the window.
- **Config:** `[song]` table (`SongSettings`): `wait` (default on), `one_key`, `any_octave`, `song_layout` (default on), `metronome`, `count_in`, `auto_speed`, `backing`, `offset_ms`, `beats_visible`, `best`, `recent`, `listen_input`, `listen_gate_db`, `listen_basic`.
- **Headless testing:** like before (Xvfb + xdotool), but `xdotool windowfocus` first or keys don't arrive. The ALSA null device runs **faster than real time**, so a song without wait mode finishes in a second there: timing can't be judged headless (it's covered by the unit tests in `songplay.rs` / `practice.rs`). A fake microphone for Listen: an `.asoundrc` with an `asym` PCM whose capture side is `type file` with `infile` pointing at raw S16_LE 48 kHz stereo.
- **Not checked on real hardware:** how the sync feels on Bluetooth earbuds (the maths is tested, the feel isn't), and live listen on a real microphone / monitor source.
- Ideas not done: playing the analyzer's stems as the backing (Part 7; `Song.stems` is parsed), time-stretching the stems, editing chords in the editor, app-side transpose of a whole song to any key, practising hands separately with different keys, a "show me" demo that plays your part with the keys lighting, saving what Listen heard as a song, spaced repetition of the bars you miss most, MIDI-file metadata (title/artist) beyond the track name.

### From Part 2

- **Layouts are just keymaps.** Piano / Chords + Melody / Isomorphic / Drums are built-in keymap files (`Keymap::builtin`, `BUILTIN_LAYOUTS`), written to `~/.config/qwertone/keymaps/` if missing. The Play tab decides what panels to show from the actions a keymap contains (`Keymap::has_kind`), so a user's custom layout that mixes chords and drums just works.
- **Keys are `KeyId`** (`Key(egui::Key)` | `Shift` | `Ctrl` | `Alt`). egui reports modifiers only as state, so `raw_input_hook` turns `Event::ModifiersChanged` (and each key event's `modifiers`) into press/release of those KeyIds via `sync_modifiers`. Left/right can't be told apart. Ctrl/Alt + key is passed to egui as a shortcut only if the layout doesn't bind Ctrl/Alt.
- **New actions:** `melody n`, `chord <1-7 | roman numeral>`, `mod 7th|sus4|add9|swap`, `drum <name|num>`, `rhythm`, `style±`, `tempo±`, `scale+`, `scale-lock`, `layout+`. Each needs `parse`, `Display`, `describe`, a `kind()`, and (controls) an entry in `CONTROLS` + an icon in `widgets::control_icon`.
- **Theory** (`theory.rs`): `Scale` (8 scales; pentatonic/blues borrow chords from their parent major/minor), `ChordRef::{Diatonic(1..7), Fixed{root, quality}}`, `build_chord(ref, mods, tonic_pc, scale)` → name + roman numeral + intervals, `voice_chord` (tries every inversion near the centre, minimises movement from the previous voicing, with a pull back to the centre so it never drifts). The key's tonic is `cfg.transpose mod 12`. Chords are voiced around G3 regardless of key; bass is the root in octave 2; melody tonic = base note + 12 (C4 at octave 0).
- **Audio channels:** 0 melody (pedal logic in `Renderer`), 1 chords, 2 bass, 9 drums (GM percussion; rustysynth treats channel 9 as drums). The built-in synth now has a patch per channel and a small synthesised drum kit, so everything works without a SoundFont.
- **Sequencer** (`audio/sequencer.rs`) runs in the audio thread: block / strum / arpeggio / pattern styles, its own sample clock, scheduled note-offs with per-note generation counters (a re-struck note isn't cut by the old note's off). `Renderer::render_block` splits each buffer at the sequencer's next event, so timing is sample-accurate. Commands: `Chord{chord, retrigger, velocity}` (`None` = key released, `retrigger=false` = only a modifier/key/scale changed → only changed notes move), `Style`, `Pattern(Arc)`, `Tempo`, `Rhythm(bool)`, `Drum`, `ChannelProgram`. Stats expose `seq_running/seq_step/...` for the beat dots.
- **Bluetooth "grace" window:** a chord change pressed shortly after a step replays the most recent step that had chord notes, with the new chord. Window = 80 ms + 0.8 × the device's measured latency (max 320 ms), so people reacting to delayed sound still land on the beat. The same idea can line up Part 5's scoring.
- **Patterns** (`audio/patterns.rs`) are TOML grids (one line per part, one char per step). Built-ins are in code; `~/.config/qwertone/patterns/*.toml` add to / override them (first run writes `shuffle.toml` as an example). The UI keeps every `Arc<Pattern>` alive (including replaced ones) so the audio thread never frees memory.
- Latch ("keep playing after I let go", default on) applies to arpeggio/patterns; for block/strum the pedal does the same. A modifier/key change while latched sends `Chord{Some, retrigger:false}` then `Chord{None}`.
- New config keys (all `#[serde(default)]`): `scale`, `scale_lock` (off, so Part 1's piano is unchanged), `show_scale`, `voice_leading`, `chord_bass`, `style`, `tempo`, `strum_ms`, `arp_mode`, `arp_rate`, `arp_octaves`, `drums`, `latch`, `chord_instrument`, `bass_instrument`. Instruments appended to `INSTRUMENTS` (indices of old ones unchanged); `BASS_SOUNDS` is separate.
- Part 1 keymaps get `F1 = layout+` added once (migration in `config::load_keymap`, only for files with no `layout+` text at all).
- Tested headless under Xvfb with an ALSA null device (`pcm.!default { type null }` in `~/.asoundrc`) and xdotool; handy for screenshots in later sessions.
- **Instrument pictures** (`ui/visuals.rs`): `Visual::for_program` picks keyboard / guitar / strings / flute / waveform from the GM program (drums layout → pads); `cfg.visual` = "auto" or a fixed one. Fretboards use `place_notes` (each note on its own string, smallest hand stretch; more notes than strings drops the lowest). The flute chart is a 6-hole simple-system flute/whistle in C (half-holes + one cross fingering), not a Boehm flute; same holes an octave up. Drum pads flash from `drum_hits` (only keys you hit, not the pattern's drums: those happen in the audio thread; exposing them would need a hit ring-buffer in `Stats`). The waveform is drawn from the note frequencies, not the real audio output.
- **Saved devices** (Audio tab): lists `cfg.devices` with rename (sets `DeviceProfile.label`, which now wins over PipeWire's description everywhere via `device_name`), re-test (only for the connected device) and remove (two clicks). Saving a test result no longer overwrites a custom name.
- Ideas not done: count-in, fills / variations per pattern, swing amount, tap tempo, per-pattern default tempo, chord inversion keys, recording the chord progression (Part 4 looper can reuse the `Chord` commands as events).
